## 5.2 开发与调试约定

1. **始终在插件目录内改**：`app/Plugins/CostTracking/`。除「核心确实没有钩子」外，不修改核心代码。
2. **必须加核心钩子时**：只加一行 `@dispatchEvent('xxx.yyy', [..])`，载荷带齐模板变量；同时更新 [03-改动清单.md](03-改动清单.md)。
3. **模板事件里只 echo HTML**：统一用 `costtracking_render('视图名', $data)`，它已包 try/catch，绝不让插件异常打挂核心页面。
4. **类式过滤器必须 return payload**；事件不要有返回值依赖。
5. **读数用 Repository，不要在 register.php 里直接写 SQL**；批量场景走 map 接口防 N+1。
6. **防御式取值**：模板事件载荷可能被 `leantime`/`laravel` 包装，取键一律走 `costtracking_context()`；事件对象的 id 可能为 null。
7. **清缓存意识**：改了模板结构/INI 后，清 `storage/framework/viewPaths.php`、`storage/framework/views/*` 与 installation 缓存。
8. **语法检查**：提交前对改动的 PHP 文件跑 `php -l`；Blade 改动通过页面实测（无 Blade lint 流水线）。
9. 日志统一前缀 `[CostTracking]`，便于在 `storage/logs/laravel.log` 过滤。

## 5.3 常见扩展场景手册

### 场景 A：给成本增加第三个字段（如「资本性支出 capex」）

1. `Services/CostTracking.php`：`install()` 的 Schema 加列（只影响新装）。
2. 按 §5.7 加 enable 期补丁，给已装环境补列。
3. `Repositories/Costs.php`：upsert 参数、`normalizeRow()`、rollup 的 `selectRaw`/返回结构全部加字段。
4. register.php `$saveCosts`：加 `$_POST['costtracking_capex']` 读取，并把「字段存在才 upsert」的判断更新。
5. `formFields.blade.php` 加输入框（name 用 `costtracking_` 前缀）；列表/角标/Tab 模板按需加展示。
6. 两个 INI 同步加键。

### 场景 B：增加一个只读的成本报表页（需要控制器+路由）

1. 建 `Controllers/Costreport.php`（命名空间 `Leantime\Plugins\CostTracking\Controllers`），按核心控制器约定 `run()` 方法 + 显示模板。
2. 建插件根目录 `routes.php`，用户插件的路由在 `pluginsEvents` 时由 RouteLoader 加载（参考基线文档 §7.2「路由」行）。
3. 视图 `Templates/costReport.blade.php`，用 `view('costtracking::costReport', ...)`。
4. 需要菜单入口时在 register.php 用 `(new Registration('CostTracking'))->addMenuItem([...], 'project', [...])`。
5. 需要权限控制时建 `Permissions/CostTrackingPermissions.php`（PermissionRegistry 自动发现），控制器/方法加 `#[RequiresPermission(...)]`。

### 场景 C：加定时任务（如每周成本快照邮件）

在 register.php 监听核心调度事件，载荷 `$params['schedule']` 是 Laravel `Schedule` 实例（与 Queue/Reports 域 register.php 用法一致）：

```php
use Illuminate\Console\Scheduling\Schedule;

EventDispatcher::add_event_listener('leantime.core.console.consolekernel.schedule.cron', function ($params) {
    if (get_class($params['schedule']) !== Schedule::class) {
        return;
    }

    $params['schedule']
        ->call(fn () => app(\Leantime\Plugins\CostTracking\Services\CostTracking::class)->someWeeklyJob())
        ->name('costtracking:weekly-snapshot')
        ->weekly();
});
```

### 场景 D：加 CLI 命令

建 `Command/XxxCommand.php`（目录名 `Command`，ConsoleKernel 自动发现），签名示例 `costtracking:recalculate`，可在里面调用 Repository 重算/修复数据。

### 场景 E：引入较重的 JS/CSS（需要构建产物时）

当前插件刻意零构建。若后续确需复杂交互：

1. 在插件内建 `dist/` 并产出 Mix manifest（核心 Registration 会把插件 `dist` 目录加进 manifest 搜索路径）。
2. register.php 用 `(new Registration('CostTracking'))->addCss([...])` / `addFooterJs([...])`，**不要**继续手写 `<script>` 引用未构建源码。
3. 简单样式/几行 JS 仍优先内联，避免维护构建链。

### 场景 F：把成本数据开放给 JSON-RPC API / MCP

- 只读服务方法放进插件 Service 并按核心约定加 `@api` 注解的方式不适用于插件命名空间；插件要暴露 API 时优先走「场景 B」的控制器返回 JSON，或监听核心 API 相关过滤器扩展方法表。
- MCP 工具同理：优先通过核心提供的工具注册过滤器挂载，不要复制核心工具类。
- 实施前先在核心代码中确认对应扩展点确实存在（grep `dispatch_filter` / `dispatchEvent`），没有扩展点时再评估最小核心改动。

## 5.4 红线清单（Review 时一票否决）

- 🚫 改 `zp_tickets` / `zp_projects` 结构或往核心迁移目录加脚本、改 `AppSettings::$dbVersion`。
- 🚫 覆盖（override）核心类、改核心 Service 的白名单/保存流程。
- 🚫 在监听器里做自己的权限判断绕过核心，或在核心权限校验前的位置写库。
- 🚫 把成本列插到 showAll 行首 / 改 tfoot 单元格数（破坏 DataTables 固定索引 0–13 的语义）。
- 🚫 在里程碑表格输出列（破坏列对齐）。
- 🚫 用 `request()` helper（本仓库没有该全局函数）；直接读 `$_POST`/`$_GET` 并做白名单校验。
- 🚫 GET 参数不做白名单就拼进逻辑/SQL（口径参数限定枚举）。
- 🚫 在循环里逐条查成本（必须用 map / 批量汇总接口）。
- 🚫 硬编码颜色不用 CSS 变量（深色模式会坏）。
- 🚫 只改一种语言文件导致键缺失（虽然有英文兜底，仍要求双语同步）。

## 5.5 跟随上游升级的 Checklist

核心升级后，按此清单回归：

1. **`.gitmodules` 冲突**：upstream 若仍带 `app/Plugins` submodule，合并时保留我方删除状态：
   ```powershell
   git rm .gitmodules 2>$null
   git rm --cached app/Plugins 2>$null
   git add app/Plugins
   ```
   并确认没有重新生成 `.git/modules/app/Plugins`。
2. **核心钩子是否还在/载荷是否变化**：
   - `beforeEndRightColumn`（两处 submodule 模板）
   - `allTicketsTable.beforeHeadRow / beforeRowEnd / afterClose`
   - `projectTabsList / projectTabsContent`
   - 本插件新增的 3 个 `@dispatchEvent` 是否在合并中被冲掉。
3. **showAll 列数**：grep `ticketsController.js` 中 `.ticketTable` 的 DataTables 配置，确认核心仍是 14 列、`columnDefs`/`footerCallback` 索引未变；若核心列数变化，同步修改 `tableHeaderExtra.blade.php` 的占位 `<th>` 数量（始终 = 核心列数 + 2），并确认 body 单元格数。
4. **事件类**：`TicketCreated/Updated/Deleted/TicketListFilter` 的属性名与派发点（grep 四个类名）。重点：
   - 新建任务派发是否仍带新 ticketId；
   - `TicketListFilter` 载荷是否仍是 `['items'=>...]` 分组结构、派发前的行数。
5. **模板上下文名**：`currentEvent` 仍按 `leantime.domain.tickets.templates.{path}.{hook}` 生成；若视图改名（如 showAll 改名），更新 register.php 里的 `str_contains` 判断。
6. **Registration API**：`registerLanguageFiles()` 签名、`addMenuItem()` 等是否变更。
7. **视图发现**：升级后若 `costtracking::` 命名空间失效，删 `storage/framework/viewPaths.php` 让其重新发现。
8. 跑一遍 [04-安装与验证手册.md](04-安装与验证手册.md) §4.4 的 1–15 号用例。

## 5.6 已知技术债 / 注意点

1. **表前缀硬编码 `zp_`**：`CostTracking::TABLE` 与 Repository join 的 `zp_tickets` 写死了默认前缀。若实例安装时改了表前缀，需改为从核心配置（数据库连接的表前缀配置）动态拼接。升级处理时建议一次性在 Repository 内引入私有 `table()` 辅助方法。
2. **无独立迁移框架**：插件只有 install/uninstall 两时机。已安装实例的结构演进必须在 `enable()` 中做幂等补丁（§5.7），不要假设管理员会重装。
3. **金额为裸 decimal**：无币种、无税口径。多币种需求出现前不要提前加字段。
4. **请求级缓存依赖容器单例**：若未来把 Repository 注册为每次解析新实例，批量缓存会退化为 N+1，改动时需同步评估。
5. **DataTables 多行表头方案**依赖 1.13 行为（每列主 cell 取底行）。升级 `datatables.net` 大版本时必须回归 showAll 的排序/列可见性。
6. **项目 Tab 的预算口径**：当前「使用率」= 实际成本 / `dollarBudget`。若未来引入「预算成本 vs 项目预算」的偏差分析，注意页面上同时存在两个「预算」概念，文案要区分（字段标签可改为「任务预算合计」）。

## 5.7 插件内「数据库结构升级」标准模式

插件没有核心那套 `$dbUpdates`。对已安装实例，在 `enable()` 里做幂等演进（enable 每次启用都会执行）：

```php
// Services/CostTracking.php
public function enable(): bool
{
    try {
        if (! Schema::hasColumn(self::TABLE, 'capex')) {
            Schema::table(self::TABLE, function (Blueprint $t) {
                $t->decimal('capex', 12, 2)->nullable()->after('actualCost');
            });
        }
        // 后续新列继续追加 hasColumn 判断；禁止写「else 回滚」
        return true;
    } catch (\Throwable $e) {
        Log::error('[CostTracking] enable migration failed: '.$e->getMessage());
        return false;
    }
}
```

约束：只增不删、每步独立判断、失败返回 false 并留日志；不要在 enable 里做数据回填之外的数据删除。

## 5.8 测试建议

- **最小自动化**：为 `Repositories/Costs.php` 加集成测试（核心测试基建见 [.docs/initial-0910/11-构建测试与部署.md](../initial-0910/11-构建测试与部署.md)）：用事务回滚隔离，覆盖 ① 两种口径互斥不双算 ② NULL 不计入 ③ 里程碑排除 ④ upsert 幂等。
- register.php 的监听器偏胶水代码，以 §4.4 的手工用例回归为主；其中 `costtracking_amount()` 这类纯函数适合抽成可单测的静态工具（若后续逻辑变复杂，建议把全局函数迁移到独立 `Support/` 类）。
- 提测前固定回归三件事：showAll 核心列、里程碑页、看板拖拽不清空。

## 5.9 后续演进路线（按价值排序，供排期参考）

1. **成本校验与体验**：输入框改为带千分位/币种后缀的格式化控件；负数与超大值拦截。
2. **项目/项目集报表**：按负责人、里程碑、时间段的成本汇总（场景 B + D）。
3. **预算预警**：实际成本达到预算阈值时经核心通知系统提醒（复用 Notifications 域扩展点）。
4. **快照与趋势**：可选的每周快照表 + 简单趋势图（再评估是否引入「历史」需求，当前明确不做）。
5. **多币种**：需先有项目级币种字段的产品方案，不建议在插件内单独发明。
6. **表前缀动态化**（技术债 1）与 **Repository 集成测试**（§5.8），建议在第 2 项之前先还。
